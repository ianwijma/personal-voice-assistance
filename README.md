# personal-voice-assistance

Created in [T3 Code](https://t3.codes).

A personal voice assistant that runs on your Linux machine. You talk, it answers out loud, and it can call tools (the clock and the weather so far) to look things up. **Everything runs locally except the language model:** speech recognition, turn detection and speech synthesis use [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) models on the CPU, so the only key you need is the language model's. Hosted speech providers (Deepgram, Cartesia, ElevenLabs) remain available as options.

Two goals decide the design:

1. **Low latency.** The number that matters is the time from the end of your sentence to the first sound of the reply. Target: under 800 ms. Measured on the development machine with local speech (Parakeet v2) and a simulated 300 ms model: **median 771 ms, worst 1095 ms** (see [Measured latency](#measured-latency)).
2. **Easy to extend and to swap.** A new capability is one file plus one line. A new provider is one package plus one line. Several assistants can run at once, each with its own prompt, language model, hearing, voice and modules.

Node 22, TypeScript, Effect 4, pnpm workspace. The design and the service contracts are in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

> **Status.** The local pipeline (speech in → recognised → turn detected → reply generated by the offline stand-in model → synthesised → written to WAV) has run end to end on the development machine, and so has the web UI: the real page in headless Chromium, with a fake microphone fed from WAV files, against the real assistant (`pnpm e2e:real`). It has **never** run with a real microphone and speaker (no sound card), never on a real laptop or phone, and never against the real Anthropic, Deepgram or Cartesia services (no keys). See [What has been verified](#what-has-been-verified).

## How it works

```
microphone ─pcm 16 kHz─▶ STT (local sherpa-onnx + Silero VAD, turn detection) ─events─▶ Conversation ─▶ LLM (Claude) + tools
     ─text─▶ clause chunker ─▶ TTS (local Piper, child process) ─pcm 22 kHz─▶ speaker
```

- Local models are loaded and warmed up at startup (about 1–2 s). Hosted connections open at startup and stay open; the LLM connection is warmed up.
- Text goes to TTS one clause at a time, as soon as each clause is complete, so the reply starts playing before the model has finished.
- **Speculative turns:** when the STT reports that you have *probably* finished (`EagerEndOfTurn`, after 250 ms of silence), the reply is generated right away but held back. If you really are done (`EndOfTurn`, 600 ms of silence), it plays at once. If you keep talking, it is thrown away. Only tools marked read-only run during speculation.
- **Barge-in:** if you start talking while the assistant is speaking, it stops. Only the part you actually heard is kept in the history.
- **Assistants and devices:** an **assistant** is a configuration you create in the admin page (`/admin/`): a prompt, a language model account and model, how it hears (speech model, turn timing), one voice and which modules it may use. A **device** (a browser today) says which assistants answer on it, which wake phrase wakes each one ("Hey Jeff", "Hey T3"), and who answers a sentence without a phrase: nobody, one assistant, or TypeSafe (hosted, optional) choosing from each assistant's description. Each device has its own conversation with each assistant, and several devices can talk at the same time. A **route gate** reads the transcript and picks the assistant; a **session dispatcher** keeps one conversation per assistant and one speaker per device; a **resource pool** shares what is equal (one language model instance, one loaded speech model, one voice) between assistants and devices and builds a changed one before switching, without a reload. Design, status and measurements: [docs/ASSISTANTS.md](docs/ASSISTANTS.md); the protocol (version 7) is in `packages/protocol`.

## Quick start

Requirements: Node ≥ 22.18, pnpm 10, `tar` with bzip2, about 800 MB of disk for the default models (Kokoro adds 400 MB) and 2.5 GB of free memory. Voice mode also needs PipeWire (`pw-record` and `pw-cat`).

```sh
pnpm install
pnpm download-models          # default STT (Parakeet v2 + Silero VAD) and TTS (Piper en_US-lessac-medium), into models/ (or later from Settings)
# everything else is set in the web UI (pnpm serve → Settings); .env only for the few startup variables

echo "what's the time?" | pnpm start text      # text mode; works offline with the stand-in model
pnpm start say "Hello, I run on this machine."   # plays on the speaker (or add --out hello.wav)
pnpm start bench --make-wavs bench-audio       # synthesise five test questions with the local voice
pnpm start bench --live bench-audio            # local end-to-end benchmark (stand-in model, WAV output)
LLM_PROVIDER=anthropic pnpm start voice        # on a machine with a microphone: talk to it, Ctrl+C to quit
pnpm serve                                     # the web UI: the browser is the microphone and speaker (see below)
```

`pnpm check` typechecks every package and `pnpm test` runs all unit tests (no network, no keys; the tests that load real models skip when the models are absent). There is no build step: packages export their TypeScript sources and the app runs with `tsx`.

Optional models: `pnpm --filter @pva/tts-sherpa download kokoro-af_heart` (the Kokoro voice), `pnpm --filter @pva/tts-sherpa download nl_NL-pim-medium` (Dutch), `pnpm --filter @pva/stt-sherpa download-models parakeet-ultra whisper-turbo nemotron-560 hybrid-nemotron-parakeet` (other speech recognisers, see [Speech recognition models](#speech-recognition-models)).

## Configuration

**Configure everything under Settings in the web UI** (`pnpm serve`, then the gear or `O`). Values are saved in
`data/settings.json`, keys in an encrypted key vault outside the project (see [Keys & access](#keys--access)). Every
page says what a choice implies (hosted, needs a key, not downloaded, slower start) and what it needs, and a speech
model that is not on this machine yet is downloaded from the same page. The command-line modes (`text`, `voice`,
`say`, `bench`, `transcribe`) read the same saved settings and keys; they use the shared settings and the flat keys (`LLM_PROVIDER`, `ANTHROPIC_MODEL`, `STT_SHERPA_MODEL`, `ASSISTANT_VOICE`, …) that became per-assistant settings in serve mode (a data directory from before assistants is migrated into one assistant at the first start of `serve`, and a copy of the old file is kept).

| What | Where in Settings |
|---|---|
| An assistant: prompt, tool rounds, follow-up, new conversation after a quiet spell | Assistants › the assistant › Behaviour |
| Language model: offline stand-in, Claude API (key), Claude subscription, OpenRouter, a home model server; model, effort, limits | Assistants › the assistant › Language model; the accounts under Shared settings › Language model accounts |
| Speech recognition: on this machine (model, language, turn timing, microphone processing) or Deepgram | Assistants › the assistant › Hearing; Deepgram key and the model list under Shared settings › Speech recognition models |
| Speech and voice models: download, cancel, delete | Shared settings › Speech recognition models, Voice providers |
| The assistant's voice (any provider's voice, preview, favourites) and the Cartesia and ElevenLabs keys | Assistants › the assistant › Voice; Shared settings › Voice providers |
| Modules (clock, weather, Home Assistant, …): which assistant has which, their shared and own settings | Assistants › the assistant › Modules; Shared settings › Modules |
| Which assistants answer on which device, wake phrases, who answers without a phrase | Devices (a device, or "Every browser") |
| Location, time zone, language, units (the modules' defaults) | Shared settings › Home |
| TypeSafe routing (key, model) | Shared settings › Routing |
| Keys, the vault password, who may change what | Keys & vault |
| What `.env` or the environment still sets, and **Move to settings** | Diagnostics › Settings from outside |

**`.env` holds almost nothing.** Only these are read before the settings exist ([`.env.example`](.env.example)), all
optional:

| Variable | Default | What |
|---|---|---|
| `PVA_ADMIN_PASSWORD` | unset | the admin page's password (`/admin/`, at least 8 characters). Unset or shorter: admin is disabled and nothing can be configured from a browser |
| `PVA_VAULT_PASSWORD` | unset | unlocks the key vault at start (otherwise unlock it in the UI after each restart) |
| `PVA_DATA_DIR` | `<repo>/data` | where the settings are |
| `SERVE_HOST`, `SERVE_PORT` | `127.0.0.1`, `8787` | where the UI listens (anything but loopback exposes it to your network) |
| `SERVE_TLS_CERT`, `SERVE_TLS_KEY` | unset | both set: HTTPS (the microphone needs it off localhost) |

Anything else in `.env` or exported by the shell still works and wins over the saved settings (environment > saved >
default), and the field shows where it comes from ("Set by STT_SHERPA_AGC in /…/.env, line 3"). For a variable from
`.env`, **Move to settings** (on the field, or Diagnostics › Settings from outside, also *Move all*) saves the value
(a key into the vault; refused while the vault is locked) and comments its line out of the file, keeping a backup
next to it (`.env.bak-<time>`, mode 0600) and the file's mode; the value is never logged or sent to a page. That page
also lists variables nothing reads (often a typo).

The command-line modes unlock the vault with `PVA_VAULT_PASSWORD`, or ask for the password when run in a terminal
(Enter skips it; providers that need a key then fail and say the vault is locked).

**For development** (read from the environment only, not shown in the UI): `AUDIO_BACKEND` (`pipewire` | `file`),
`AUDIO_INPUT_FILE`, `AUDIO_INPUT_TRAILING_SILENCE_MS`, `AUDIO_OUTPUT_DIR`, `PIPEWIRE_*` (CLI audio), `BARGE_IN`,
`BENCH_*` (benchmarks; `BENCH_LLM_FIRST_TOKEN_MS` / `BENCH_LLM_TOKENS_PER_S` also give the offline stand-in a
simulated speed in serve mode), `SERVE_ALLOWED_ORIGINS`, `PVA_WEB_DIR`, `PVA_VAULT_PATH`, `DEEPGRAM_URL`,
`CARTESIA_URL`, `ELEVENLABS_URL`, and the web mock's `MOCK_*` / `E2E_MOCK_PORT`. The adapter READMEs list every provider setting by
its variable name ([stt-sherpa](packages/stt-sherpa/README.md), [tts-sherpa](packages/tts-sherpa/README.md), [tts-elevenlabs](packages/tts-elevenlabs/README.md)), which is
also the key it is saved under.

`fake` is an offline LLM stand-in: it answers time questions through the clock tool and echoes everything else. It is the default so that text mode works without any key. **For real use choose Anthropic (with an API key) or the Claude subscription** as the account on an assistant's Language model tab (Assistants › the assistant). The accounts themselves are set up once, under Shared settings › Language model accounts (the Anthropic key there; for the Claude subscription, see below).

**Claude subscription** (`claude-subscription`): the language model is Claude Code with the login of the `claude` program on this machine, so replies count against your Claude plan's limits instead of an API bill ([`@pva/agent-claude-code`](packages/agent-claude-code/README.md)). Anthropic's terms for using a subscription from other software are unclear, so the *Claude subscription* module is off by default and has its own opt-in switch. Under Shared settings › Language model accounts, switch on *Use my Claude subscription* in the *Claude subscription* block and save, then switch the module on there (it refuses to start without the opt-in); then choose *Claude subscription* as the account on an assistant's Language model tab. It takes effect from the next turn, no reload. While the module is off, starting or failed, the offline stand-in answers and first says so ("Claude subscription is off — switch it on in Settings, Language model."). Claude Code gets only a short allowlist of environment variables (`PATH`, `HOME`, locale, proxy and CA settings, `CLAUDE_CONFIG_DIR`, …), never other providers' keys or the vault password.

If a required setting or a model file is missing, a command-line mode lists every problem, with the stage it belongs to and how to fix it, and exits (serve mode shows the same problems in the admin Overview and keeps running):

```
Cannot start (settings go in the environment or in .env; see .env.example):
  voice (ASSISTANT_VOICE): Model file for TTS preset "en_US-lessac-medium" is missing: /…/models/vits-piper-en_US-lessac-medium/en_US-lessac-medium.onnx. Download it from an assistant's Voice tab, or run: pnpm --filter @pva/tts-sherpa download en_US-lessac-medium
  speech-to-text (STT_PROVIDER): DEEPGRAM_API_KEY is not set
```

### Speech recognition models

The local recogniser is chosen on an assistant's **Hearing** tab (`STT_SHERPA_MODEL` in the command-line modes; the choice
reloads the engines, and if the reload fails the running one keeps running). A model that is not downloaded yet
shows **Download** with its size right there, and Save waits until it is there. The same section sets the language, the two end-of-turn pauses, the speech
detection threshold and the gain control, each with an explanation of what it trades.

| Preset | For | Trade-off |
|---|---|---|
| **`parakeet-v2`** (default) | English | Most accurate (about 13 % word errors on phone-like audio, where the previous default had 34 %); reads your whole sentence when you pause, so the reply starts 0.1–0.5 s later than with a streaming model for long sentences; words appear about once a second while you talk |
| `parakeet-ultra` | English and Dutch (and 23 more European languages) | Nearly as accurate and as fast; picks the language itself, which very poor audio can confuse |
| `whisper-turbo` | Dutch in noise, 99 languages | Most robust for Dutch, but the reply starts 1–3 s after you stop and no words appear while you talk |
| `hybrid-nemotron-parakeet` | Seeing your words live | Nemotron shows the words as you speak, Parakeet makes the text that is answered; 1 GB more memory and more CPU |
| `nemotron-560` | Live words, multilingual, less memory | 2–3× the errors of Parakeet |
| `nemotron-320` | The previous default (`nemotron-3.5`) | The least accurate of the large models |
| `zipformer-en`, `fast-conformer-en` | Small machines, English | Not recommended: the worst on real-world audio |

**Downloads from the UI**: Shared settings › Speech recognition models and an assistant's Voice tab list every preset with its size and state
(installed, downloading x %, not downloaded) and offer Download, Cancel and Delete (a model the running engines use
cannot be deleted). Only a page with edit access can start one; every page sees the progress. A download checks the
free disk space first (download plus unpacked size), fetches into a `.part` file (60 s without data fails it),
checks the size, unpacks at low priority (`nice -n 10 tar -xjf`) into a temporary folder, checks the expected files,
and only then moves the model into place; cancelling or a failure removes the partial files (and a restart removes
what an interrupted one left). It runs on the server, so closing the page does not stop it. Measured effect on
replies: [While a model downloads](#while-a-model-downloads).

From a terminal the same code runs: `pnpm --filter @pva/stt-sherpa download-models <preset>` (`--list` shows which
are installed and their sizes) and `pnpm --filter @pva/tts-sherpa download <preset>`. Details, licences and
measurements: [stt-sherpa README](packages/stt-sherpa/README.md).

## Running

Every mode runs through the app's `start` script. From the repository root, `pnpm start <mode>` is a shortcut for `pnpm --filter @pva/assistant start <mode>`. Relative paths on the command line are resolved from the directory you run the command in.

### Text mode

A stdin/stdout chat over the same conversation and tool code that voice mode uses, with the same system prompt (including the voice instructions). Replies go to stdout with any voice markers removed. One latency line per turn goes to stderr.

```sh
pnpm start text                               # interactive
echo "what's the time?" | pnpm start text     # one-shot, works offline
LLM_PROVIDER=anthropic pnpm start text        # real model
```

### Voice mode

```sh
LLM_PROVIDER=anthropic pnpm start voice
```

Voice mode listens on the default PipeWire source and speaks on the default sink until you press Ctrl+C. Startup loads the local models (about 2 s). Ctrl+C stops the engine processes and the audio processes and closes every socket. For each turn it prints what it heard and what it answered on stdout, and the latency line on stderr. These lines come from a run with the file backend and the offline stand-in model (a barge-in test: the second question interrupts the first reply):

```
you: After early nightfall, the yellow lamps would light up here and there the squalid quarter of the brothels
assistant: You said: [interrupted]
turn #1 voice (speculative) interrupted llmRequestSent=-232ms llmFirstToken=-231ms (+1ms) firstClause=-216ms (+15ms) ttsFirstAudio=-184ms (+32ms) playbackStart=0ms (+185ms) voices: standard total=461ms
you: Thanks that's all for now
assistant: You said: Thanks that's all for now
turn #2 voice (speculative) completed llmRequestSent=-256ms llmFirstToken=-256ms (+0ms) firstClause=-241ms (+15ms) ttsFirstAudio=-218ms (+23ms) playbackStart=0ms (+218ms) voices: standard total=1925ms
```

To use a file instead of a microphone, run `AUDIO_BACKEND=file AUDIO_INPUT_FILE=question.wav pnpm start voice`. The file must be 16 kHz WAV (16-bit or 32-bit float). Silence around it is a −75 dBFS noise floor, like a quiet microphone. Replies are written to `audio-out/reply-NNN.wav`, and the program exits after the last reply.

### Web UI (serve mode)

To run it from a container image (Kubernetes included), see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

```sh
pnpm serve     # builds the UI (apps/web/out), then starts the assistant serving it on http://127.0.0.1:8787
pnpm dev       # development: the assistant on :8787 and the UI with hot reload on http://localhost:3000
```

`pnpm serve` is `pnpm --filter @pva/web build` followed by `pnpm start serve`; `pnpm start serve` alone serves the last build. In `pnpm dev` the page reloads as you edit `apps/web`; the assistant itself does not restart on changes (restart `pnpm dev` after server changes; the engines load in about 2 s), and the dev page connects to `ws://<page host>:8787/ws`. In both modes Ctrl+C stops everything: checked on the development machine, no Next, tsx or engine process is left (pnpm then prints `ELIFECYCLE Command failed`, which only reports the Ctrl+C).

One process on one port serves the UI and a WebSocket at `/ws`. The browser becomes the assistant's microphone and speaker: press **Start** on the page. Any number of tabs (at most 8) can be open; one owns the audio and the others see the conversation and play nothing ("Use this tab" moves the audio). Without a built UI the page says how to build it; the assistant runs anyway.

The admin page (`/admin/`) has **Assistants** (one page per assistant: Basics, Behaviour, Language model, Hearing, Voice, Modules, Used on; and a seven-step wizard for a new one), **Devices** (who answers where, wake phrases, interrupting, audio, captions, a phrase tester), **Shared settings** (Home, modules, language model accounts, speech recognition models, voice providers, routing, limits), Keys & vault, Diagnostics (Latency, with the assistant, device and route of each turn) and About. A module runs while an assistant has it on; a change applies from the next turn and a tool call in progress finishes. Saved values go to `data/settings.json`; secrets such as API keys go to the key vault (below; before you set a password, to `data/secrets.json` at mode 0600 as before). The browser can set or remove a secret but never read it. `PVA_DATA_DIR` moves the data directory. Environment variables and `.env` win over saved values and lock the field in the UI (with **Move to settings** for a `.env` line; see [Configuration](#configuration)). Settings marked *reload* take effect after **Reload engines**, which rebuilds the speech and language engines in about 2 s and keeps the conversation.

Settings: `SERVE_HOST` (default `127.0.0.1`), `SERVE_PORT` (8787), `SERVE_ALLOWED_ORIGINS` (other page origins allowed to open the socket; default the Next dev server on port 3000), `SERVE_ALLOWED_HOSTS` (host names the server answers to besides IP addresses, `localhost` and the origins' hosts; any other name gets HTTP 403, against DNS rebinding), `SERVE_BEHIND_PROXY` (default `false`; `true` when a reverse proxy is in front, see below), `SERVE_TLS_CERT` + `SERVE_TLS_KEY` (PEM files; with both, the server speaks HTTPS/WSS on the same port), `SERVE_CROSS_ORIGIN_ISOLATION` (default `true`: COOP/COEP/CORP headers make the page cross-origin isolated, so it reads how much of a reply played straight from the player), `PVA_WEB_DIR` (default `apps/web/out`), `PVA_DATA_DIR` (default `data/`), `PVA_VAULT_PATH`, `PVA_VAULT_PASSWORD` (below). Ctrl+C closes the sockets, the engine processes and the modules.

**If the page does not load (or Start fails) on a particular browser**, restart the assistant with `SERVE_CROSS_ORIGIN_ISOLATION=false` (in `.env` or the service's environment) and reload the page. If that fixes it, cross-origin isolation is the cause: the page works without it, with a slightly less exact count of what was heard when it is closed in the middle of a reply. Tested in Chromium only; not yet on iPhone Safari.

#### Keys & access

Settings → **Keys & access** (every protected page also takes the password inline):

1. **Set a password** (at least 8 characters, typed twice). The keys in `data/secrets.json` move into an encrypted file outside the project, `~/.config/pva/vault.enc` (`$XDG_CONFIG_HOME/pva/vault.enc`, or `PVA_VAULT_PATH`; mode 0600 in a 0700 directory), and `data/secrets.json` is deleted; the page says how many keys moved. From then on every key entered in the UI is stored only there.
2. **After every restart the keys are locked.** Engines and modules that need a key do not start ("Keys are locked — unlock them in Settings → Keys & access"); local speech and the Claude subscription keep working. Type the password (the banner on the stage has a password field too): the failed engines reload and failed modules restart by themselves. To run unattended, put the password in `.env` as `PVA_VAULT_PASSWORD`, the one secret meant for `.env`: the vault then unlocks at start (a wrong one is logged and leaves it locked). It is never logged, taken out of the environment at start and never passed to Claude Code.
3. **Who may change what.** Since protocol 5 every change (settings, modules, keys, the vault, downloads, front ends, devices) is made on the admin page (`/admin/`), after logging in with `PVA_ADMIN_PASSWORD` from `.env` (read once at start, taken out of the environment, never logged). Without it admin is disabled and nothing can be configured from a browser. A login lasts at most 12 hours, ends after 30 minutes without a change, at **Log out**, and when the assistant restarts; after 5 wrong passwords in a row logins are refused for 30 s, then the wait doubles. Unlocking the vault needs both: an admin page and the vault password. The voice page (`/`) only talks to the assistant and changes its own voice and activation.
4. **Lock now** removes the keys from memory (admin logins stay; running engines keep the keys they started with until they are reloaded). **Change password** re-encrypts the vault with a new salt.
5. **Forgot the password?** Delete the vault file; the keys in it are lost and you enter them again. There is no other way in.

The vault is `node:crypto` only: scrypt (N = 2¹⁷, r = 8, p = 1, a random 16-byte salt, parameters in the file; unlocking took 289 ms on the development machine) and AES-256-GCM with a fresh 12-byte IV per write, the header authenticated. A wrong password and a modified file both fail to open, and the file is never reset. After 5 wrong passwords in a row, unlocking is refused for 30 s, then the wait doubles.

**Reaching it from another device.** Browsers allow the microphone only on `https://` pages or on `localhost`, and this machine has no sound card, so the microphone and speaker are always another device. The assistant binds to `127.0.0.1` and has **no login**: anyone who can reach the port can use it and change its open settings (once a vault password is set, keys, providers and agents need that password; see [Keys & access](#keys--access)). Routes, simplest first:

1. **SSH tunnel** (a laptop on your network; the recommended route):
   1. On the assistant machine: `pnpm serve` (leave it running; it stays on `127.0.0.1`).
   2. On the laptop: `ssh -N -L 8787:localhost:8787 user@assistant-host` (leave it running; `-N` means no shell).
   3. On the laptop, open **`http://localhost:8787`** in Chrome or Edge (only Chromium is tested), press **Start talking** and allow the microphone. `localhost` counts as secure, so no certificate is needed.
   4. On open speakers keep the default *Speakers: say a few words*; with headphones choose *Headphones: instant* (Settings → This device → Microphone & speaker), where **Test echo** also tells you whether your browser cancels the assistant's voice.

   For `pnpm dev`, forward both ports and open `http://localhost:3000`: `ssh -N -L 3000:localhost:3000 -L 8787:localhost:8787 user@assistant-host`.
2. **HTTPS on the assistant** (a phone, which cannot open an SSH tunnel easily): set `SERVE_TLS_CERT` and `SERVE_TLS_KEY` to a certificate the device trusts (your own CA installed on the device, or a real hostname with a DNS-01 certificate), and `SERVE_HOST=0.0.0.0`, then open `https://<that hostname>:8787` on the phone. The server warns when it listens beyond loopback. Not tried on a real phone yet.
3. **A reverse proxy** in front of the default loopback binding (Caddy, `tailscale serve`), which terminates TLS. Add the proxy's public origin to `SERVE_ALLOWED_ORIGINS` if it differs from the `Host` the server sees, and its host name to `SERVE_ALLOWED_HOSTS` if the proxy passes that name on as `Host`. Set `SERVE_BEHIND_PROXY=true`: the server cannot tell a proxied request from a local one, so then no caller counts as on the home network and module web addresses guarded by "home network" refuse every request (callers from outside use an address that needs a token). The proxy must pass `Host` through unchanged (Caddy and `tailscale serve` do by default): a browser's request to a module web address that is not public is then judged same-origin by the host and port of its `Origin` against `Host`, ignoring the scheme the proxy terminated.

**Echo and interrupting.** Each device chooses how speech interrupts the assistant (Settings → This device → Microphone & speaker): *Headphones: instant* (any speech stops the reply), *Speakers: confirm* (the default: the assistant stops once the recogniser has two words that are not its own echo; one-word "stop" does not interrupt, use the Stop button), or *manual* (only Stop; the microphone is muted while the assistant speaks). The server-side echo gate implements these; the browser's echo cancellation is also requested.

**Testing it without a browser.** A scripted client speaks a WAV into a running server and prints the message timeline and each turn's latency trace:

```sh
LLM_PROVIDER=fake SERVE_PORT=8799 pnpm start serve &
pnpm --filter @pva/assistant exec tsx test/support/drive.ts --url http://127.0.0.1:8799 bench-audio/01-hello-can-you-hear-me.wav
```

Observed on the development machine (2026-11-13, local STT nemotron-3.5, Piper, fake LLM, scripted client on the same machine): the speculative reply was promoted and the client reported `playback.started` 2–4 ms after `EndOfTurn` in four turns; from the end of the speech audio to `turn.start` and `playback.started` 635 and 657 ms in the two turns where that was timed (the 600 ms final silence dominates, as in the CLI). The trace's `playbackStart` includes the WebSocket hop and the browser's report; `audible` adds the browser's `outputLatency`. For the real browser see [Through the browser](#through-the-browser).

**Testing it with the real page.** `pnpm e2e:real` builds the UI and runs the page in headless Chromium against the real assistant (local speech models, `LLM_PROVIDER=fake`), with Chromium's fake microphone playing 48 kHz WAVs made from `bench-audio/`: a spoken turn, barge-in in `instant` and `confirm` mode, `manual` mode, a typed message, Stop, two pages with a takeover in the middle of a reply, the server killed and restarted in the middle of a reply, and modules changed from the options drawer (11 tests, about 1.5 minutes; each test file starts its own assistant on its own port, 8791–8798, with its data under `apps/web/test-results/real/`). It builds the UI into `apps/web/out-e2e/`, never over `apps/web/out/`, so an assistant already serving `out/` is not disturbed. One test checks that the page is cross-origin isolated as configured, that the worklets load and use the shared counter, and that Stop gives an exact final count; run it once more with `SERVE_CROSS_ORIGIN_ISOLATION=false pnpm e2e:real` to check the page without isolation. It skips when the models, `bench-audio/` or Chromium are missing (`pnpm start bench --make-wavs bench-audio`, `pnpm --filter @pva/web e2e:install`). `pnpm bench:browser` measures latency through the browser (below); `pnpm --filter @pva/web screenshots:real` rewrites `apps/web/screenshots/real-*.png`. The assistant's output and each page's message log are kept under `apps/web/test-results/real/`.

### On a phone (iPhone Safari or Brave)

The page works on iOS (Safari, and Brave, which uses the same WebKit engine) over HTTPS. Settings → **This
device** has settings that matter more on a phone than elsewhere, stored per device:

- **Microphone processing**: echo cancellation, noise suppression and automatic gain, each switchable
  (changing one re-opens the microphone). On iOS, echo cancellation switches on Apple's voice processing,
  which also changes the level and sound of your voice and, on iOS 26.2 and later, can make playback crackle
  ([WebKit bug 326286](https://bugs.webkit.org/show_bug.cgi?id=326286), open). Without it the assistant hears
  its own voice on the loudspeaker: use headphones, or set *Interrupting* to *Tap Stop*.
- **Audio diagnostics**: the microphone's real sample rate and processing flags as the browser reports
  them, and playback counters (underruns, gaps, clicks smoothed, the lowest buffer level). **Copy report**
  puts them on the clipboard.
- **Advanced → Prebuffer** (up to 500 ms) and **Output path** (*Direct* or *Through a media element*).

If the assistant mishears you or playback pops, see [Is it the audio or the model?](#is-it-the-audio-or-the-model)
and [Popping in playback](#popping-in-playback).

### Is it the audio or the model?

To find out why a sentence was misheard:

1. Settings → Diagnostics → Recordings → **Save what the assistant hears** (on). From then on every turn's audio,
   exactly as the server received it (before its gain control), is saved in `data/recordings/` as a WAV file
   with a `.json` beside it (the transcript, the model, levels, band and transport counters); the newest 50
   are kept (*Recordings kept*, advanced). The server log gets one line per turn, for example:

   ```
   Heard (sherpa parakeet-v2): "What's the weather in Amsterdam?" — peak -31.2 dBFS, speech -45.0 dBFS RMS, floor -71.3 dBFS,
   SNR 26.3 dB, clipped 0 %, band to ~7.6 kHz (4.1 % above 3.4 kHz); quiet (peak below -18 dBFS) — data/recordings/2026-…-001.wav
   ```
2. Speak a few sentences from the phone, then turn it off again.
3. Run every installed model on those recordings (one model loaded at a time, about a minute for a few files):

   ```sh
   pnpm start compare-models data/recordings                    # every installed preset
   pnpm start compare-models --ref "The birch canoe slid on the smooth planks." data/recordings/<file>.wav
   pnpm start compare-models --agc both --models parakeet-v2,nemotron-320 data/recordings
   ```

   It prints each file's levels and, per model, the transcript, how many turns it became and when the
   speculative and final texts came after the speech; with `--ref`, the word error rate.

How to read it: *too quiet* (peak below −30 dBFS) or *noisy* → the audio; switch the phone's processing
switches and record again. *Narrowband* (energy ends near 3–4 kHz) → a Bluetooth headset or phone-call
audio path; use the phone's own microphone. Only one model wrong → the model. A sentence split into
several turns → pauses longer than *Pause that ends your turn*. Non-zero `droppedFrames`, `lostOnTheWay` or
long `maxMicGapMs` in the `.json` → frames lost or delayed on the network.

### Popping in playback

Reported from an iPhone; it cannot be reproduced here (no sound card, no iPhone). What was found in the
code and fixed (player worklet, `apps/web/worklets/player.js`, tested in `apps/web/test/worklets/player.test.ts`
at 48, 44.1 and 24 kHz):

- **An underrun jumped to silence and back.** When reply audio arrived late (the 60 ms prebuffer ran dry, as
  happens when Wi-Fi delivers packets in bursts), the output dropped from the current sample to zero within
  one sample, and jumped back when audio resumed: two clicks per underrun. Now every edge (a dry queue,
  resuming, the start of a reply, the end, one reply cutting off another) is bridged by a 3 ms de-click
  ramp, so a gap sounds like a gap.
- **A reply that replaced another one was cut hard**, and the first sample of a reply was played at full
  level: both are ramped now.
- **Repeated underruns kept refilling only 40 ms**, so a slow link stuttered on. Each underrun in a reply
  now doubles the refill target (40, 80, 160, 320 ms).
- Checked and fine: the 22 050 → 48 000 / 44 100 / 24 000 Hz resampling is continuous across frame and
  clause boundaries (bit-identical to resampling the whole reply at once), and fades on Stop were already
  ramped.

Remaining hypotheses, most likely first, and what to try (Settings → This device):

1. **iOS voice processing crackle** ([WebKit bug 326286](https://bugs.webkit.org/show_bug.cgi?id=326286):
   output crackles while a microphone with echo cancellation is open, iOS 26.2–27; open, no fix). Turn
   **Echo cancellation** off (with headphones, or *Interrupting: Tap Stop* on the loudspeaker). If the pops
   stop, this is it. Users report that output may then move to the earpiece at a lower volume.
2. **Late audio (underruns).** If *Audio diagnostics* shows underruns, raise **Prebuffer** to 200–300 ms.
   Each underrun is now a short, soft gap instead of a pop.
3. **The output path.** Switch **Output path** to *Through a media element* and compare (an older WebKit
   workaround for output problems while the microphone is open; [bug 218012](https://bugs.webkit.org/show_bug.cgi?id=218012)).
4. **Sample-rate switching when the microphone opens** (iOS changes its audio session when capture starts;
   [bug 236219](https://bugs.webkit.org/show_bug.cgi?id=236219), [bug 311451](https://bugs.webkit.org/show_bug.cgi?id=311451)).
   Compare the reported microphone sample rate with the audio context's in *Audio diagnostics*; try
   headphones.

Report back: **Copy report** in *Audio diagnostics* after a few replies, with echo cancellation on and off.

### Trying a voice or an STT provider: `say` and `transcribe`

Two quick-test commands try an engine without a conversation. Both stop with the startup message above if a key or a model is missing.

```sh
pnpm start say "Hello, this is the assistant's voice."           # plays on AUDIO_BACKEND
pnpm start say --voice sherpa:kokoro-af_heart "Once upon a time." # another voice, for this run (provider:voice)
pnpm start say --out hello.wav "Write it to a file instead."
pnpm start transcribe models/test-wavs/0.wav                     # 16 kHz WAV
```

`say` sends the text through the same clause chunker as a conversation, then prints the time from its first clause to its first audio, the total synthesis time, the length of the audio, and the real-time factor (synthesis time ÷ audio length; below 1 is faster than real time). Measured before voice providers (2026-11-14, Piper and Kokoro):

```
standard: first audio 74 ms, synthesis 75 ms, audio 1.63 s, real-time factor 0.05 (1 clauses)
natural: first audio 498 ms, synthesis 505 ms, audio 3.04 s, real-time factor 0.17 (1 clauses)
```

(Measured on the development machine: Piper, then a 14-word Kokoro clause. A 9-word sentence alone takes Kokoro about 275 ms to first audio, Piper about 70 ms.) `transcribe` streams the file in real time through `STT_PROVIDER`, then silence until an end of turn arrives (at most `AUDIO_INPUT_TRAILING_SILENCE_MS`). It prints every event with its time since the start and relative to the end of the speech audio (negative = before the audio ended), for example, with the local STT on `models/test-wavs/0.wav` (the clip ends with about 0.4 s of quiet, so the eager end of turn comes before the file ends):

```
+  562 ms  audio end - 6063 ms  SpeechStarted
+ 6584 ms  audio end -   41 ms  EagerEndOfTurn "After early nightfall, the yellow lamps would light up here and there the squalid quarter of the brothels"
+ 6821 ms  audio end +  196 ms  EndOfTurn "After early nightfall, the yellow lamps would light up here and there the squalid quarter of the brothels"
```

### Reading the latency line

Each mark is in milliseconds relative to **end of turn**, the moment the STT decided you had finished. The value in brackets is the time since the previous mark.

| Mark | Meaning |
|---|---|
| `llmRequestSent` | the request to the model left |
| `llmFirstToken` | the first word of text came back (after any tool round) |
| `firstClause` | the clause chunker handed the first clause to TTS |
| `ttsFirstAudio` | the first audio chunk came back from TTS |
| `playbackStart` | the first audio chunk went to the speaker: **the headline number** |
| `tools:` | how long each tool call took |
| `voices:` | the voices that spoke in this turn (voice mode) |
| `total` | when the turn ended (reply finished, or interrupted) |

**Negative values** mean the work happened before the end of turn. This is a speculative turn (started on `EagerEndOfTurn`) that was then confirmed. The outcome is `completed`, `interrupted` (barge-in), `discarded` (a speculative turn you talked over) or `failed` (provider error; the conversation keeps running).

The end-of-turn mark does not include the time the STT took to decide you had stopped talking. The live benchmark measures that separately (its `eager` and `eot` columns, from the end of the audio).

### Benchmarks

**Offline (no keys, runs anywhere):**

```sh
pnpm start bench
```

This runs a scripted four-turn conversation through the real `Conversation` orchestrator. STT, LLM, TTS and the speaker are replaced by in-process stand-ins with simulated delays. One turn uses a tool, and one has a false start where the user keeps talking after an eager end of turn. It runs three scenarios and prints a per-turn table plus median and worst case for each:

1. **All delays zero:** the overhead the orchestration itself adds between end of turn and first audio.
2. **Realistic delays, eager end-of-turn off:** LLM first token 250 ms, then 60 tokens/s; TTS first audio 150 ms.
3. **The same with eager end-of-turn on:** `EagerEndOfTurn` arrives 200 ms before `EndOfTurn`. This shows what speculative turns save.

The delays can be changed with the `BENCH_*` variables in `.env.example`. Results on the development machine (median / worst): overhead **0.8 / 1.6 ms** (measured with the voice router, which has since been removed); realistic without speculation **508 / 735 ms**; with speculation **307 / 535 ms**. The worst case is the tool turn, which needs two model calls.

**Live (the real pipeline):**

```sh
pnpm start bench --make-wavs bench-audio                   # five test questions, synthesised with the configured TTS, resampled to 16 kHz
pnpm start bench --live bench-audio                        # local STT + local TTS + the fake LLM (simulated 250 ms first token, 60 tok/s)
BENCH_LLM_FIRST_TOKEN_MS=300 pnpm start bench --live --rounds 4 bench-audio   # stand in for a 300 ms hosted model, 20 turns
LLM_PROVIDER=anthropic pnpm start bench --live bench-audio # the real model
```

`--live` takes WAV files and/or directories of them (16 kHz mono, 16-bit or 32-bit float); `--rounds N` repeats them. It plays each file as one user turn into the selected STT, LLM and TTS, all in one conversation, with the file audio backend. After each file it feeds silence (a −75 dBFS noise floor) until the reply has finished, so the turn detector fires and turns never overlap. Replies are saved to `bench-out/reply-NNN.wav` for listening. With `LLM_PROVIDER=fake`, the stand-in model waits `BENCH_LLM_FIRST_TOKEN_MS` before its first token (or tool call) and then streams at `BENCH_LLM_TOKENS_PER_S`, so a fully local run shows what a hosted model of that speed would give.

Every column is measured from the end of the file's audio: `eager` (STT `EagerEndOfTurn`: the speculative reply starts), `eot` (`EndOfTurn`: the reply may play), `1st token`, `1st clause` (handed to TTS), `tts audio` (its first audio) and `PLAY` (first audio handed to the speaker: what the user experiences). Under the table it prints what the STT heard for each file, and how often the user "resumed" (a pause long enough for an eager end of turn).

## Measured latency

Development machine, 2026-11-13: AMD Ryzen 9 7945HX (16 threads), 30 GB RAM, CPU only, no sound card (file audio backend). Local STT and Piper TTS, `LLM_PROVIDER=fake` with a simulated **300 ms to first token** and 60 tokens/s standing in for a hosted model. 21 turns per row: the five `bench-audio` questions (Piper voice, resampled to 16 kHz) plus two LibriSpeech clips (`models/test-wavs/0.wav`, `1.wav`, which has pauses mid-sentence), three rounds each. Command:

  pnpm start bench --live --rounds 3 <dir with the 7 files>
```

**With the new default STT** (2026-11-14, same machine; the five `bench-audio` questions, 3 rounds = 15 turns,
`BENCH_LLM_FIRST_TOKEN_MS=300 pnpm start bench --live --rounds 3 bench-audio`), and the previous default
model through the same adapter in the same session (`STT_SHERPA_MODEL=nemotron-320 STT_SHERPA_AGC=false`):

| STT model | eager | eot | 1st token | 1st clause | tts audio | **PLAY median / worst** |
|---|---|---|---|---|---|---|
| `parakeet-v2` (new default) | 397 | 660 | 730 | 746 | 771 | **771 / 1095** |
| `nemotron-320` (previous default model) | 393 | 681 | 716 | 731 | 756 | **757 / 1081** |

+14 ms at the median for these 2–3 s questions (the study predicted +0.01–0.08 s for 3–5 s turns), every
turn speculative and promoted, every transcript right; Nemotron heard "like an Amsterdam" in all three
rounds and returns no final punctuation. Long sentences cost more (a 16 s sentence: about +0.4 s, see the
stt-sherpa README). The table below is the earlier measurement (21 turns including two LibriSpeech clips,
so not directly comparable).

End of user audio → reply playback start, median / worst (ms), with the median of each step (2026-11-13, before the change):

| STT model | eager / final silence | eager | eot | 1st token | 1st clause | tts audio | **PLAY median / worst** |
|---|---|---|---|---|---|---|---|
| `nemotron-3.5` | 250 / 600 (default) | 372 | 641 | 691 | 706 | 729 | **729 / 1100** |
| `nemotron-3.5` | 200 / 600 | 341 | 641 | 655 | 671 | 692 | **701 / 1062** |
| `nemotron-3.5` | 200 / 400 | 344 | 441 | 654 | 671 | 693 | **693 / 1065** |
| `zipformer-en` | 250 / 600 | 344 | 660 | 666 | 683 | 705 | **705 / 1050** |
| `zipformer-en` | 200 / 400 | 285 | 460 | 606 | 622 | 645 | **645 / 992** |

Every turn was speculative and promoted (the eager transcript equalled the final one); the worst case is always the tool turn ("What time is it in Tokyo"), which needs two model calls (2 × 300 ms). Transcripts were right apart from small slips ("like an Amsterdam", "octapuces", zipformer's "T O KYO"); `1.wav` was split by its pauses (`TurnResumed`) in one of three rounds (in two with zipformer at 200 / 400). Zipformer is English only, upper case and unpunctuated, but its finalise is faster and it needs a third of the memory.

How to read it:

- **Turn detection dominates.** About 640 ms of the ~730 ms is waiting for silence: the VAD's hold-over plus the 600 ms final silence. Once `EndOfTurn` arrives, the reply is usually already synthesised (the speculative turn started at `eager`), and plays within 50–90 ms.
- **With a 300 ms model, the final silence is not the bottleneck below ~600 ms:** the speculative reply needs `eager` + 300 ms, about 650–700 ms after the audio ends. Cutting the final silence to 400 ms saved only 8 ms at the median, while making it likelier that a pause mid-sentence ends your turn. An earlier eager end of turn (200 ms) saved about 30 ms. The defaults stay at 250 / 600 ms: 30 ms is small next to the risks, which these clean test clips cannot show. Every pause longer than the eager threshold starts a speculative model request (paid, with a hosted model) and makes the STT finalise a segment, losing context at the join (see the stt-sherpa README). Try `STT_SHERPA_EAGER_SILENCE_MS=200` if your speech has few pauses.
- **The local engines are fast:** first clause → first Piper audio 20–30 ms; the STT's finalise adds about 100 ms (Nemotron) or 30 ms (zipformer) to the eager end of turn.
- **CPU:** during a turn the whole app used about 2 cores at the median and 5.2 at peak (main process with the STT about 2–3.6 cores while you speak, Piper up to 3.8 cores in bursts), out of 16. No contention on this machine; on a 4-core machine try `STT_SHERPA_THREADS=2` and `TTS_SHERPA_THREADS=2` (not measured).

### While a model downloads

Run on the development machine (16 cores) on 2026-11-14: `bench --live --rounds 6` over two test clips
(`models/test-wavs/0.wav`, short; `1.wav`, a long sentence), local Parakeet v2 + Piper, the offline stand-in with
`BENCH_LLM_FIRST_TOKEN_MS=250`, 12 turns each. "During unpack": the real downloader (`downloadArchives`) looping on a

so the unpack ran through every turn). Milliseconds from the end of the clip's audio:

| Turns | eager (median) | tts audio − 1st clause (typical) | PLAY median, short clip | PLAY median, long clip | PLAY median / worst, all 12 |
|---|---|---|---|---|---|
| Idle | 27 | 23–31 | 321 | 1269 | **790 / 1442** |
| During unpack | 61 | 23–55 | 353 | 1250 | **812 / 1414** |

### Through the browser

The same pipeline with the browser as microphone and speaker (2026-11-13, same machine): `pnpm bench:browser` speaks the five `bench-audio` questions twice into the real page in headless Chromium (fake microphone, 48 kHz) against `pnpm start serve` with `BENCH_LLM_FIRST_TOKEN_MS=300`. End of speech is the moment the page sent the last microphone frame of the question; *play* is when the page reported `playback.started` (its player handed the first sample to the audio device); *audible* adds the `outputLatency` the browser reports. For comparison the CLI benchmark was run again right before it with the same ten questions (`BENCH_LLM_FIRST_TOKEN_MS=300 pnpm start bench --live --rounds 2 bench-audio`).

| 10 turns, median / worst (ms) | end of turn | play | audible |
|---|---|---|---|
| CLI (file backend), same session | 651 / 702 | **765 / 1067** | (no device) |
| Browser (headless Chromium) | 663 / 707 | **779 / 1130** | **817 / 1178** |

Every turn was speculative and promoted; the worst is again the Tokyo time question (two model calls). The 729 ms of the table above was a different run (21 turns including two LibriSpeech clips); the turn detector varies by a few tens of ms between runs, so compare rows measured together.

What the browser adds, from the traces:

- **Between the first synthesised audio and `playback.started`: 5–21 ms, median about 11 ms.** That is the WebSocket hop (about 1 ms), the page handing the frame to the player worklet, the worklet waiting for its next render callback (the headless audio device renders 512-frame blocks, 10.7 ms; a real device usually has smaller ones), and the report back. The 60 ms prebuffer costs nothing here: the first clause arrives whole (`startDelayMs` 0 in every turn), so the player starts at once.
- **End of turn about 12 ms later** than in the CLI: the page sends 20 ms frames, and capture runs through the browser's audio processing. The browser's capture latency before the frame is sent is not in these numbers (on a real device typically 10–20 ms).
- **Output latency** as reported by headless Chromium: 29–64 ms, median 44 ms. A real device reports its own (wired: tens of ms; Bluetooth: often 150–250 ms).

No avoidable delay was found in the browser path: the reply audio is sent as soon as it exists, `reply.start` goes out when the turn is promoted, and the player starts on the first chunk. The cost is the device's render block and output latency, which only a real device can measure.

The latency readout in the page (top right, and per reply in the chat) shows the trace from the **end of the turn** (by design, §3.9 of the UI design), so it read 93–174 ms for these turns (about 500 ms for the tool turns), not the ~800 ms from the end of your speech: the ~650 ms the turn detector waits for silence happens before the trace starts.

## Adding a module

A module is a named capability the owner can switch on and off and configure. While it runs it contributes tools (things the model can call), context providers (short facts sent with every turn in the request's `context` field, separate from the cached system prompt), optional stable instructions for the system prompt, and a one-line status shown in the UI. [`packages/modules-builtin/src/weather.ts`](packages/modules-builtin/src/weather.ts) is the example of a new way to fetch information: it calls Open-Meteo over HTTP, has a timeout setting, returns a compact result the model can speak from, and turns every failure into a `ToolError`. [`clock.ts`](packages/modules-builtin/src/clock.ts) shows a context provider.

1. Write a file exporting `defineModule({ id, name, description, settings, start })`. Settings are declared with `Setting.text`, `secret`, `number`, `boolean`, `choice` and `multichoice` (optionally with `env: "NAME"`, so an environment variable can set and lock the field); the UI renders the form from them. `start` receives the validated settings and `setStatus`, runs in its own scope (acquire timers and sockets with `Effect.acquireRelease`), and returns `{ tools, context, instructions }`. Check credentials in `start`, so a bad key shows as a start error on the module rather than as a failing tool mid-conversation.
2. Define tools with `makeTool({ name, description, parameters, speculative, execute })`. `parameters` is an Effect `Schema`: it validates the model's input and produces the JSON Schema the model sees. Set `speculative: true` only for read-only tools; speculative turns run them before the user has finished. Give network tools a short timeout, because the user is waiting.
3. Return failures as `ToolError`. The model receives the message and can explain the problem.
4. Add the module to `moduleCatalog` in [`apps/assistant/src/modules.ts`](apps/assistant/src/modules.ts). The order there is the display order and the order of instructions in the prompt. Every mode uses the catalog: `serve` with live changes, the CLI modes with the saved settings.
5. Test it without the host: `resolveSettings(module.settings, { stored, secrets: {}, env: {} })`, then `Effect.scoped(module.start({ settings, setStatus }))`, then call its tools through `makeToolRegistry`. See `packages/modules-builtin/test/weather.test.ts`, which injects a fake `fetch`.

## Adding or swapping a provider

Each pipeline stage is a service interface in `packages/core` (`Llm`, `Stt`, `Tts`, `AudioInput`, `AudioOutput`; see the architecture document for the exact contracts). To add a provider:

1. Create a package (e.g. `packages/tts-elevenlabs`) that implements the interface and exports a layer reading its settings from the environment. Provider SDKs may only be imported inside their own package.
2. Add it as a dependency of `apps/assistant` and add one line to the matching map in [`apps/assistant/src/providers.ts`](apps/assistant/src/providers.ts), for example `elevenlabs: ElevenLabsTts.layerConfig`. A layer may fail at build time with the stage's error (`TtsError`, `SttError`, e.g. a missing model); its message is shown at startup, so make it say how to fix the problem.
3. For a voice provider, also add its entry to `ttsProviderInfo` and its voice list (`makeVoices`) to `hostedTtsVoices` (see [Voices](#voices)); then choose one of its voices. Add its variables to `.env.example`, and compare it with the old provider using `say` and `bench --live` on the same WAV files. For a new STT provider, `transcribe` shows its event timing on a WAV file.

## Echo cancellation (barge-in over open speakers)

Without echo cancellation the microphone hears the assistant, and the STT reports that as the user speaking. The assistant then interrupts itself. With headphones this is not a problem. With open speakers, either set `BARGE_IN=false` or route audio through PipeWire's echo-cancel module. [`packages/audio-pipewire/README.md`](packages/audio-pipewire/README.md#echo-cancellation-for-barge-in-over-open-speakers) has the config snippet. Point the assistant at the virtual nodes it creates:

```

**Not verified:**

- No real microphone or speaker, ever: the development machine has no sound card. All speech input was clean synthetic (Piper) or read (LibriSpeech/FLEURS) speech from WAV files, with no room noise, no far-field audio and no echo. Microphone gain matters for the VAD (see the stt-sherpa README).
- Nobody has listened to the output. The WAVs in `bench-out/` (gitignored, regenerate with `say --out` and `bench --live`) are there to listen to.
- No real language model: latency with Anthropic is extrapolated from the simulated 300 ms first token, not measured.
- Echo cancellation and barge-in over open speakers: the headless browser never hears its own output, so `confirm` mode was tested only with a second sentence in the input file, not with real echo (PipeWire echo-cancel snippet untested too). Whether a real browser cancels the assistant's voice (Options → This device → Test echo, with both output paths) is unknown.
- The web UI on a real device: a laptop through the SSH tunnel, a phone over HTTPS with a real certificate, real `outputLatency`, Bluetooth, speaker selection, Safari and Firefox. Nobody has listened to the browser's playback.
- Deepgram, Cartesia and ElevenLabs have never been called for real.
- Thread counts were tuned on one 16-thread machine; a 4-core machine will behave differently.
